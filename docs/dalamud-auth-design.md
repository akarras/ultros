# Ultros Dalamud account connection and token security

Date: 2026-10-18. Status: security contract with a connected prototype implementation. Device pairing, scoped bearer authorization, refresh rotation/reuse revocation and protected Windows storage are implemented; see [implementation/validation status](dalamud-prototype-status.md). This document also contains full-release requirements beyond the light prototype. Prior reviews audited the design and local CRDT experiment, not a security certification of the connected implementation. Read alongside the [plugin plan](dalamud-plugin-plan.md), [CRDT interop design](dalamud-crdt-interop.md), and [audit reconciliation](dalamud-audit.md).

The game plugin receives credentials for a restricted Ultros device grant. It never receives a Discord access token, refresh token, client secret, or browser session cookie. Discord OAuth establishes the account in the system browser; a separate explicit approval grants that installation access to selected Ultros features.

## Existing website authentication

[`oauth.rs`](../ultros/src/web/oauth.rs) currently builds a Discord authorization-code request with an S256 PKCE challenge and random OAuth state. The callback checks the saved state and uses the verifier for code exchange. The confidential client's secret and token exchange remain in the Ultros server. Its HTTP client disables redirects and has a timeout.

The returned Discord access token is stored in an encrypted `PrivateCookieJar` browser cookie. In production the cookie is host-only, `Secure`, `HttpOnly`, `SameSite=Lax`, and scoped to `/`; when supplied, the provider's expiry controls its maximum age. The server decrypts it to validate the Discord user. Successful validation is cached for at most five minutes, and logout attempts provider revocation and invalidates the local cache. This is the existing browser mechanism, not a token suitable for copying into a plugin.

These properties do not establish the security of an unimplemented plugin grant. In particular, OAuth state protects the login callback; it is not the request-forgery protection for a new device-approval POST. Logging, cross-instance invalidation, callback expiry, and provider-error handling need explicit regression coverage when the approval path is added.

## Connection flow

1. **Start in the plugin.** On an explicit Connect action, request the chosen scopes over HTTPS. The server issues independent 256-bit random device and browser-selection credentials, a five-minute expiry, and a five-second minimum polling interval. The phone code is a 40-bit SHA-256 fingerprint of the browser token, encoded as eight case-insensitive Crockford base32 symbols and displayed `XXXX-XXXX`. It is unique among live challenges. Store the device-code digest, an origin-bound keyed HMAC of the normalized human code, and a separately domain-separated, origin-bound HMAC of the browser token’s digest. The plugin keeps the challenge in memory.
2. **Open the system browser.** The plugin validates the complete approval URL against its fixed configured origin and `/plugin/verify` path, with no query parameters and a canonical 256-bit `#pair=…` fragment different from the polling credential. The website strips that fragment with `history.replaceState` before app startup and posts it to a same-origin endpoint. This endpoint validates the pending challenge and stores the token in a five-minute encrypted, host-only HttpOnly/Secure/SameSite=Lax cookie. The browser waits for capture before offering sign-in. No pairing credential enters HTTP request URLs, referrers, local/session storage, OAuth state/next, or telemetry. The game still displays the bare verification page and short code for phone/manual entry. Browser selection tokens can never poll or authenticate game APIs.
3. **Authenticate and review.** Complete the existing Ultros/Discord login, returning to the clean verification URL. The pending-link cookie preserves the request through this round trip. An authenticated browser-only approval bootstrap creates the usual approval session. If it has a pending link, a same-origin, CSRF-protected POST selects that challenge automatically and removes the pending cookie. Otherwise the player types the short phone code and uses the existing CSRF-protected selection POST. Both return the same consent component, showing the authenticated account, matching code, client label and requested permissions. No link, GET, or login completion alone approves a client. Expired or consumed links show an error and can fall back to manual entry or a new game request.
4. **Approve explicitly.** An authenticated, same-origin, CSRF-protected POST binds the pending attempt to that account and the approved scope subset. Account identity and permissions come from the browser session and server allowlist. GET, following an email/link, or finishing Discord login alone never approves a device. Denial and expiry are terminal.
5. **Redeem once.** The plugin polls using the high-entropy device code in a POST body. Before approval it receives a pending result. Approval permits one atomic transition to consumed and issuance of an Ultros access/refresh pair. Requested scopes cannot change during polling. A concurrent redemption cannot mint a second family. A lost initial response requires a new pairing attempt rather than reopening the consumed grant; unclaimed grants count against the device cap and are visible for revocation.
6. **Store and connect.** Keep the access token in memory, protect the refresh token using the supported OS credential backend, and authenticate Ultros HTTP/WebSocket requests. Cancel and clear pending connection secrets when the attempt ends, the user disconnects, or the plugin unloads.

The complete-link/manual-code interaction follows [RFC 8628 §3.3.1](https://www.rfc-editor.org/rfc/rfc8628.html#section-3.3.1), with a stronger, dedicated browser-selection credential in the complete URI. The URL credential still identifies only the pending request; existing account sign-in and explicit approval are required.

This is an Ultros device-authorization flow backed by the existing browser login, not a Discord device grant. The polling pattern avoids a local listener and supports using a separate browser device. Native apps that use a redirect-based flow instead should follow authorization code plus PKCE. References: [RFC 8628](https://www.rfc-editor.org/rfc/rfc8628.html), [native app browser guidance](https://www.rfc-editor.org/rfc/rfc8252.html).

## Approval protection

The existing Discord cookie is stateless, so add an explicit short-lived approval-session record. After browser authentication, a same-origin browser JSON request creates a random 256-bit approval-session handle in an encrypted host-only Secure/HttpOnly/SameSite=Lax cookie, path `/`, with a five-minute expiry; store its digest, account ID, and CSRF-token digest in Postgres. Keep the CSRF token in the hydrated form component’s memory. Both link and code selection POSTs validate cookie, browser account, CSRF token, and exact production `Origin`, then atomically binds the selected challenge and a fresh approval nonce to that approval session. Return JSON for the Leptos consent component with the nonce and a rotated CSRF token; store their validation digests server-side, bound to session/account/challenge. Approval must match all of them and consume the selection. No process-local session state is sufficient.

Do not rely on `SameSite` or OAuth state alone. Re-check the selected account on POST so a browser account switch invalidates the form. Freeze requested scopes at creation; approval may narrow them but cannot expand them. Bearer proof for reauthorization never replaces this browser approval. A reload or expired form returns to bare code entry, rather than reconstructing state from a URL.

Approval and browser device-management routes accept the existing browser cookie session only and reject a supplied bearer credential. They cannot be authorized by a device token, even one with every plugin scope. Authenticated plugin routes accept only their dedicated bearer extractor; a browser cookie alone never authenticates them. Pairing creation and polling are public, rate-limited exceptions. Keep `AuthDiscordUser` cookie-only and do not add a bearer fallback to it. An invalid supplied bearer header fails closed, including at socket upgrade; it never silently becomes an anonymous connection.

The `/plugin`, `/plugin/verify`, and `/plugin/devices` pages are Leptos routes inside the normal website shell. Setup includes sign-in, a real package download when configured, exact Dalamud installation instructions, connection steps, first-use documentation, and troubleshooting. Consent and client management use `LocalResource` and `Action`; human codes, CSRF tokens, and approval nonces are never serialized into SSR resources or written to browser storage. The existing cookie/Origin/CSRF/nonce/expiry/scope checks remain on the JSON endpoints.

Plugin documents omit advertising, analytics, external avatars, and error-reporting scripts. They send `Cache-Control: private, no-store`, `Referrer-Policy: same-origin`, and a CSP allowing the website’s own JavaScript/WASM while blocking third-party connections, frames, and embedding. Moving across the normal-site/plugin boundary performs a document reload to apply the correct policy; browser consent requests refuse to run without the protected-document marker. Normal website navigation and theme controls remain available. The same-origin referrer policy preserves the exact Origin on browser POSTs; Chromium sends `Origin: null` under `no-referrer`, which would fail the CSRF Origin check. Game JSON endpoints retain `no-referrer`. No access/refresh token or polling device code appears in HTML, browser storage, return URLs, or telemetry. The separate browser-selection credential exists briefly in the incoming fragment and POST body, then only in the encrypted HttpOnly pending cookie until selection; it is never a login or resource-access token. Reference: [OWASP request-forgery guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

Initial limits are enforced in Postgres across replicas, not independent process counters: at most five accepted creations per IP in ten minutes and five unexpired challenges per IP; five failed code lookups per authenticated account/IP in ten minutes; twenty total code-selection/approval submissions per account in ten minutes; ten active profiles per account. Each accepted create increments the creation bucket; unknown/expired code selection increments failed lookup; each same-origin authenticated select/approve increments the submission bucket. For a selected challenge, five invalid nonce/CSRF confirmations from its bound authenticated approval session terminate that selection. Other callers cannot increment a victim selection's counter. Code failures return a generic response and no owner. IP limits are configurable for shared networks but not absent in production. Expiry and counters use server time.

The minimum polling interval is five seconds. Early polls return `slow_down`, increasing the interval by five seconds; respect `Retry-After` on throttling and use exponential network backoff. Use the connection peer as the client IP unless that peer is in an explicit configured trusted-proxy allowlist. Trusted ingress strips incoming forwarding headers and supplies its own; parse the chain from the trusted end. Ignore spoofed forwarding headers from other peers. Release tests exercise the real ingress topology.

Record approval, denial, refresh reuse, and revocation in a redacted security-event table. A successful connection adds a **New game client connected** entry to the account's security activity and website inbox through a dedicated security-event projection, since ordinary `alert_event` requires an alert ID. It does not fabricate an alert rule. Matching codes and clear initiation text reduce device-code phishing; they cannot prevent a player deliberately approving an attacker's code or prove that a labelled client is genuine. The UI must say to enter only a code from a connection they just started in their own game.

## Credentials and lifetime

The following are proposed initial defaults, to be exercised by the release tests:

| Credential | Lifetime and purpose | Persistence |
| --- | --- | --- |
| Pairing device code | Five minutes; polling and one issuance only | Plugin memory; server validation digest and terminal state. |
| Human approval code | Same five-minute attempt; selects a request, cannot redeem it | Displayed in plugin/browser; server validation digest with attempt limits. |
| Ultros access token | Fifteen minutes; only the approved account, device, audience, and scopes | Plugin memory; server stores a digest and grant reference. |
| Ultros refresh token | Rotates on use; 30-day inactivity limit and 90-day absolute device-grant limit | OS-protected plugin storage; server stores validation digests and token-family state. |
| Discord credentials | Existing website OAuth lifecycle | Existing browser/server mechanism; never copied to the plugin grant. |

Use a cryptographic RNG for a 128-bit random lookup ID and 256-bit secret in each versioned opaque token, for example `ult_a1.<id>.<secret>` / `ult_r1.<id>.<secret>`. The server stores SHA-256 of the secret and validates it in constant time after lookup, binding the record to token kind, account, device, grant version, audience, and scopes. A SHA-256 validation digest is suitable for these high-entropy random secrets; they are not passwords. A database dump must not yield usable plugin credentials. Device IDs and scopes are non-secret metadata, not authentication.

Refresh preserves the approved authority; it never increases scopes or changes accounts. Rotate transactionally, invalidate the old generation, and detect every superseded-token refresh attempt; there is no refresh retry exception in v1. Reuse revokes the family and its access tokens, records a redacted security event, and asks the player to reconnect. Accepting a known generation solely to revoke that family never authenticates another operation or issues a token. This follows the public-client refresh-token rotation requirement in [OAuth security best practice](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).

For v1, serialize refreshes and choose the simple fail-closed response-loss policy: refresh requests are never automatically retried. A timeout, crash before durable replacement, or uncertain result requires a new browser connection. Before clearing the old protected credential, attempt a bounded best-effort revoke using that known generation; if unreachable, clear it anyway and explain server revocation is unconfirmed. Do not retain a usable old secret in an unprotected retry queue. On the next browser connection, show incomplete/unused profiles and let their owner revoke them before enforcing the ten-profile cap. Never-used issued grants expire after ten minutes; existing grants still require revocation/expiry. Atomically replace the protected refresh file before publishing the replacement access token. Retain used validation digests through family absolute expiry for reuse detection.

There is no old-token grace period or response-recovery cache in v1. Fifteen-minute access reduces normal refresh/socket churn; an ordinary successful refresh is automatic and needs no browser. Ambiguous refreshes still cost a reconnect. Opus flagged that UX cost; it is a deliberate beta limitation to measure, not a claim of seamless recovery. A later bounded idempotent recovery design needs its own replay analysis and tests before adoption. Unverified credential stores require reconnecting at every game launch.

### Multiple game clients on one PC

A device profile represents one independently paired game-client slot, with its own token family, label, protected file, and notification destination. Hold an OS-wide exclusive lock, scoped to OS user + Ultros origin + profile ID, for the entire time a plugin instance uses that profile. Serialize its refreshes within that lock. A second live game process cannot load or refresh the same profile: it selects another unused remembered profile or creates and pairs another one. Never clone a refresh credential into a second profile. A crash releases the OS lock; it does not make an uncertain refresh safe to retry. Lock contention leaves item lookup usable and shows **Profile already in use — choose another profile**.

This is an operational safeguard against honest clients revoking each other, not a defense against malicious plugins. Test two game processes, plugin hot-reload, abandoned locks, and simultaneous startup. All mutable runtime state (consent preferences, queued capture state, displayed delivery IDs, last cursor) lives in per-profile files under the same lock; ordinary shared config contains only immutable defaults/non-secret profile discovery. The profile directory index uses atomic replace under its own short OS lock. The approval page and Connected devices distinguish profiles so simultaneous clients do not appear to be one device.

## Local storage and transport

On supported Windows installations, protect refresh credentials with DPAPI using `DataProtectionScope.CurrentUser` or a reviewed equivalent OS credential store. Keep protected credentials separate from ordinary plugin configuration and support exports, and limit file access to the current user. Verify behavior in the supported runtime. A Wine/other environment without a verified credential backend uses memory-only login and reconnects after restart; there is no plaintext/base64 fallback. Reference: [Microsoft data protection](https://learn.microsoft.com/en-us/dotnet/standard/security/how-to-use-data-protection).

Use a dedicated Ultros HTTP client with cookies and automatic redirects disabled, normal TLS certificate validation, and exact-origin credential binding. Never reuse its Authorization header with icon, external-link, or arbitrary response URLs. Release builds accept production HTTPS origins only. Explicit debug loopback origins use separate credential namespaces and cannot reuse production credentials. Browser/device labels are length-bounded text, never executable markup or arbitrary navigation targets.

Send the access token in the HTTP Authorization header, including the native WebSocket handshake. Never put access/refresh tokens in query parameters or WebSocket messages; the refresh token is accepted only by the refresh/revocation flow. Do not embed a client secret in the DLL: an installed public client cannot keep one confidential.

Use secret-redacting types and error formatting. Exclude Authorization, cookies, OAuth codes/state/verifiers, pairing codes, refresh bodies, and returned tokens from HTTP tracing, reverse-proxy logs, crash reports, support exports, and analytics. Add tests that inject identifiable dummy secrets and assert that captured diagnostics never contain them. Reference: [OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html).

## Scope and authorization boundaries

The initial connection preselects notifications and list reads; registration, list writes, and uploads require explicit choices. Grant only approved scope IDs from the catalogue below. Dependencies must be present in the requested/approved set, never silently added at redemption. The uploader is unchecked by default, with separate opt-in per character; missing permission opens browser approval and no upload starts while pending.

| Scope IDs / capability | Consent label | Default / dependencies |
| --- | --- | --- |
| Own-session identity and self-revoke (intrinsic, no optional scope) | Manage this connection | Mandatory for every active grant; cannot address another device. |
| `notifications:read`, `notifications:ack`, `notifications:mark-read` | Receive and manage game notifications | Default on as one indivisible bundle; acknowledgements/read changes limited to this device's eligible deliveries/events. |
| `lists:read` | Read my shopping lists | Default on; current resource permission still required. |
| `lists:write` | Edit my shopping lists | Off; requires `lists:read`. |
| `retainers:read` | View my private characters and retainers | Off; included explicitly in registration/upload consent requests. |
| `retainers:register` | Register my characters and retainers | Off; requires `retainers:read`. |
| `retainers:upload` | Save private listings for opted-in characters | Off; requires `retainers:read`, existing registration, and current-character consent. |

Use `POST /api/v1/plugin/session/reauthorize` to create a replacement-permission attempt. This route requires the old profile's valid access token; derive the old device/account/grant version from its principal, never a request-body device ID. Anonymous pairing creation rejects replacement fields. Bind the attempt to that old grant; approval and redemption require the same browser account, unchanged active grant version, and an unrevoked old device. Consent explicitly says **This replaces permissions for Gaming PC · Main**. It may approve a narrower or broader requested set, so call it reauthorization rather than assuming every change is elevation. Success replaces the family and preserves/rebinds its destination/alert links. Removing notification permission disables that destination and cancels pending deliveries, retaining its links for explicit re-enablement after another approval. Denial/expiry leaves prior permissions usable; a pending request cannot resurrect a revoked profile. Account switching clears/revokes the old local grant first and never transfers destinations between owners.

The plugin principal carries account ID, device ID, scopes, and grant version, never a fully privileged `AuthDiscordUser`. Every handler checks capability and resource permission. Every list CRDT merge checks current sharing permission; a read-only collaborator cannot write using a broad scope. Notification acknowledgement/read operations accept only eligible device/account events. Device management revokes the caller's own grant, never a body-supplied owner's installation.

The upload capability only changes account-private observations for already-registered discovered retainers. It may update observed name/world/time and re-resolve an optional public link, but creates no character/retainer/ownership row and changes no grouping. Unknown entries return `registration_required`; the explicit bulk-registration transaction requires `retainers:register`. Uploads cannot edit public retainer metadata, market boards, sales, or another account's registrations. Client assertions remain unverified.

The socket authorization matrix is an allowlist: public market subscribe/unsubscribe needs no device scope; `SubscribeListDoc` needs `lists:read` plus current permission; `ListDocUpdate` needs `lists:write` plus current write permission, enforced again inside the validated merge transaction. The initial cart grant is capped at row-write permission, so owner-only metadata changes remain forbidden even for an account owner. Device-delivery subscriptions require `notifications:read` and bind the authenticated device, never a supplied device ID. Acknowledgement/read state uses scoped HTTP routes. Broad `SubscribeNotifications`, legacy list subscriptions, and other unlisted variants remain denied. This replaces the earlier command-only policy; the plugin uses Lists 2.0 CRDT sync. New variants default to denied until reviewed.

## Revocation and account changes

The authoritative device row records owner, scopes, grant version, revocation, last use, and absolute expiry. HTTP mutations lock the account row for share, then the device row for share and revalidate it within the transaction; account deletion takes the conflicting account lock and revoke/refresh/reauthorization take the conflicting device lock. A revoke that acquires its lock first prevents the later write; a write already holding it commits before revoke. Authentication caches must not hide a revoked write grant. Deny operations if authority storage is unavailable.

For lists, lock the list row, then take `FOR SHARE` on the concrete sufficient permission path: direct share, group share plus group/membership (or ownership), or role share plus role/membership. Recheck predicates after acquiring locks; absent/changed evidence denies the update. Ordinary membership sync update/delete conflicts naturally. Lock the document and apply the validated CRDT update through the shared merge path; never bypass it with relational row writes. Keep compatible list-before-document ordering across writers. This needs transaction-aware permission helpers; today's pre-transaction `get_permission` is insufficient.

Across new transactions, lock account first, devices in ID order, then resource rows (list or alert), endpoint rows, document/snapshot/delivery rows. Alert acceptance takes participating device locks before its alert/endpoint locks (replan if its unlocked candidate set changed), and revocation uses the same device→alert→endpoint order. Worker lease claiming commits and releases its delivery lock before authorization/send; it must not acquire a device lock while holding a claim transaction. Existing paths may still deadlock under database contention: retry a whole transaction at most three times with jitter on deadlock/serialization failure, never retry an external send as part of that transaction. Prove ordering with concurrent tests.

An access token's expiry bounds a WebSocket session (at most fifteen minutes). Refresh outside the socket and reconnect with a fresh token. On the shared browser/plugin socket route, presence of an Authorization header selects the device extractor exclusively and cookies are ignored; invalid bearer proof fails the handshake. Without it, existing browser/anonymous behavior applies. Re-check current device/resource permission before protected delivery. Each replica batches all of its idle device sockets into bounded Postgres validation queries on a fifteen-second tick, checking revocation/expiry/grant version; do not execute one timer query per socket. A local cancellation bus accelerates shutdown but is not authoritative. No revocation retracts data already delivered.

Protected reads and deliveries check current grant state against Postgres, without a positive revocation cache in v1. A delivery already authorized before a revoke may be in flight; idle sockets close within 15 seconds and no newly authorized delivery begins after revocation commits. Validate expiry on each protected action as well as on the timer. Returning validation-store errors closes protected subscriptions rather than continuing on stale authority.

Provide **Connected devices**, **Revoke this device**, and **Revoke all devices** with label, account, created/last-used times, scopes, and expiry. Revoke families, disable endpoint/remove alert links, and cancel deliveries transactionally. Retain security history; reconnecting after revoke creates a new destination requiring reassignment. Reauthorization alone preserves it. Disconnect attempts revoke and clears credentials; offline UI says server revocation is unconfirmed. Preserve account-partitioned CRDT work on session expiry, following Lists 2.0 lifecycle rules; explicit permission denial/deletion purges that list's cache. Never transmit saved changes under another account. Offline edits do not override the server's decision when sync resumes.

Ordinary website logout and switching FFXIV characters do not automatically revoke an independently approved installation. Account deletion does. Revoking the Discord OAuth app is not a reliable automatic revocation signal for an independent Ultros grant; connected-device controls must make that distinction clear. Define and test account deletion concurrent with refresh, cached identity validation, and registration so an old session cannot recreate device authority after deletion.

## Security limits

The plugin opens approval links through its own HTTP(S)-only launcher and turns launch exceptions into a generic failure flag. Avoid Dalamud's `Util.OpenLink` for pairing links: its [error handler logs the supplied URL](https://github.com/goatcorp/Dalamud/blob/master/Dalamud/Utility/Util.cs). The full fragment credential and raw launch exception must never enter the game log. A missing browser handler leaves the phone-code fallback available.

OS protection reduces exposure from copied configuration files or another OS user's access. Other plugins or malware running in the same game process or OS account may still read/decrypt credentials or act as the player. No embedded secret or ordinary software key can turn the Dalamud host into an isolated trust boundary. Short lifetimes, limited scopes, refresh-reuse detection, and revocation reduce the impact; they do not promise protection from a compromised client.

The intended protection is that compromising this installation exposes a limited Ultros grant rather than the player's Discord account credential. A compromised Ultros server can act within the authority it holds; database-only token disclosure and full server compromise are different cases.

## Required security tests

- Concurrent approval/redemption on different server instances yields one bound account and one token family; expired/denied/consumed attempts cannot mint another.
- Cross-origin approval, missing/wrong CSRF, account switching, scope tampering, guessing, and aggressive polling fail closed without leaking account data.
- Only correct scoped tokens can read or mutate each resource; exercise every plugin HTTP route and socket message, including notification acknowledgements and read state.
- A notification-only/read-only token cannot submit CRDT updates. Row-write tokens cannot mutate owner metadata. Replayed frames are idempotent; expired/revoked grants cannot merge offline work, and changing accounts cannot transmit the previous account's snapshot.
- Access expiry, refresh replay, lost refresh responses, concurrent refreshes, scope downgrade, revoke-all, and account deletion behave consistently across replicas.
- Two game processes cannot refresh the same protected profile; separate paired profiles remain connected independently. Crash/reload releases the lock without retrying an uncertain refresh.
- Revocation racing with a queued write or idle socket enforces the documented bounds. An unavailable authority store cannot authenticate a mutation.
- Copied configuration/support exports contain no usable plaintext secret; unsupported secure storage results in memory-only mode.
- A response redirect, base-origin change, dummy-secret error, or diagnostics capture cannot send or print credentials outside the intended boundary.
