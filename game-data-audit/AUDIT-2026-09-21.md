# Browser game-data audit — 2026-09-21

Follow-up: the implemented startup projection and all-locale pack sizes are
documented in [data/xiv-startup](../data/xiv-startup/README.md). The measurements
below preserve the original audit experiments, before that combined projection.

## Scope and provenance

This is a data audit, not a lazy-route, caching, or application schema change.
The tool inventories 37 tables and 222 row columns directly from the Rust
schema. Source consumers were reviewed separately; the tool does **not** claim
to perform whole-program field-liveness analysis.

- Source checkout: `9b93be11` (before the compression change).
- Input: the English Brotli pack from
  [`081f770f051e034b93ef064a11978bd53e4354a1`](https://github.com/akarras/ultros/commit/081f770f051e034b93ef064a11978bd53e4354a1).
  That commit changes compression and caching, not the `Data` schema.
- Input SHA-256:
  `48957fb327c999e0b4f8e1ae549b8c457d9666cd76fff5e92198b9a6bc5aa0e4`.
  Verified against the commit's LFS pointer.
- Input: **2,746,297 bytes**; decoded rkyv: **17,036,884 bytes**.
- Whole-pack audit baseline: **2,746,296 bytes**, Brotli quality 11, lgwin 24.
  The one-byte difference from the published pack is why comparisons below
  use the audit's own baseline.
- Column ranking uses q5 to keep the full inventory quick; whole-pack
  reduction experiments and table sizes below use q11.

The source-only nature of this audit matters: no field removal was compiled
through the application, and no slimmed pack was put into a browser. The
experiments are candidate payload reductions, not deployment-ready packs.

The duplicate shop/leve equality checks also passed against all seven
checked-in legacy zlib packs (en, ja, de, fr, cn, ko, tc). Those checks validate
the invariants across those locale inputs; the q11 savings below were measured
only against the linked English Brotli pack.

## Whole-pack experiments

Each row starts from the full original data. Savings are not additive because
archive layout and compression matches change. Even a small table can affect
the compressed layout elsewhere.

| Experiment | Resulting bytes (q11) | Saved bytes | Status |
| --- | ---: | ---: | --- |
| Empty three FC metadata tables | 2,730,305 | 15,991 | Candidate-unused; no non-schema/non-generator consumer found |
| Clear duplicated `SpecialShop.item` | 2,737,859 | 8,437 | Verified equal to `item_receive_0` in all 1,489 rows |
| Zero duplicate leve arrays | 2,729,674 | 16,622 | Equality with scalar columns verified; fixed-width slots remain |
| Zero item source icon IDs | 2,685,136 | 61,160 | Extraction-only input; fixed-width slots remain |
| Neutralize generation-only location columns | 2,685,753 | 60,543 | Requires source/client type separation |
| Defer all item descriptions | 2,262,563 | 483,733 | Used by item tooltips; requires a detail-loading path |
| Retain only referenced NPC names | 2,260,313 | 485,983 | 935 names retained; direct NPC URLs require fallback |
| Descriptions and NPC reduction together | 1,768,368 | 977,928 | Approximately 35.6%; a loading architecture change |

Clearing strings/vectors keeps their descriptors. Zeroing numeric columns
keeps their fixed-width slots. These measure the cost of payload content; a
new projected schema needs its own measurement after physically removing
columns. In particular, none of the numbers promise byte-for-byte savings
after a schema rewrite, across other locales, or with other encoder versions.

## Reviewed candidates

### Generator-only source data should not define the browser contract

- `Item.icon`: icon extraction needs it in
  [game-data-pack/src/db.rs](../game-data-pack/src/db.rs). The browser's
  [ItemIcon](../ultros-frontend/ultros-ui-game/src/components/item_icon.rs)
  builds `/static/itemicon/{item_id}` URLs; the server's
  [search index](../ultros/src/search_service.rs) deliberately returns item IDs
  for images. The unrelated `link.icon` field in navigation is not a consumer
  of `xiv_gen::Item.icon`.
- `ENpcResident.map`: used to select the map during placement extraction in
  [game-data-pack/src/main.rs](../game-data-pack/src/main.rs).
- `TerritoryType.bg`, `Map.offset_x`, `Map.offset_y`: used to read game layouts
  and convert coordinates in
  [placements.rs](../game-data-pack/src/placements.rs). The client receives
  the already-computed `NpcPlacement.x/y`.
- `Map.place_name_region`: no consumer found beyond schema/fixture construction.
  Location labels do need `place_name` and `place_name_sub`; these must stay.

Keep these columns in CSV/extraction types and project only browser fields
after generation. Removing them from a shared source struct would damage the
generator even though the browser doesn't need them.

### Duplicate and apparently unused data

- `SpecialShop.item` and `item_receive_0` read the same CSV column. The real
  pack confirms equality. `entries()`, exchange selection, and related-item
  lookups use `item_receive_0`, so the duplicate is a strong removal candidate.
- `LeveRewardItem.leve_reward_item_group` duplicates the eight scalar group
  columns. `LeveRewardItemGroup.item` duplicates nine scalar item columns.
  [LeveAnalyzer](../ultros-frontend/ultros-app/src/routes/leve_analyzer.rs) and
  [leve_rewards_item](../ultros-frontend/ultros-ui-crafting/src/components/related_items.rs)
  use the scalar forms. Keep one representation and provide helper methods
  rather than storing both; the audit verifies equality before measuring.
- `company_craft_drafts`, `company_craft_draft_categorys`, and
  `company_craft_types`: no application consumer found. Do **not** remove the
  sequences, parts, processes, or supply-item tables: FC Crafting uses those.

These are reviewed candidates, not compiler-proven removals. The final check
is to remove them from the projected client schema and compile both SSR and
hydrate configurations, then regenerate and test the affected pages.

### Fields and rows that are used, but need not block every page

- Item descriptions and stat arrays support tooltips and item details. They
  are suitable for a separate detail pack or batch endpoint.
- Recipes and their level tables support real local planning and calculation.
  They are suitable for feature-specific loading, not deletion.
- NPC pruning retains all names referenced by gil/special/collectables shops,
  leve issuers, or placement keys. Arbitrary `/npc/:id` currently accepts any
  resident row; pruning without a detail endpoint changes valid direct URLs.
- Place-name/map/territory pruning should follow retained placement references
  transitively. Do not remove an apparently unused place name merely because
  one test visit did not render it.
- Base-parameter descriptions and `order_priority` are used by
  [stats_display.rs](../ultros-frontend/ultros-ui-game/src/components/stats_display.rs).
  These are examples where a plausible “metadata” deletion would break UI.
- IDs duplicated inside records are not automatically dead: many components
  use `item.key_id` after discarding the HashMap key.

## Recommended implementation order after the audit

1. Introduce explicit source-to-client projection types. Start with duplicate
   columns, the three FC metadata tables, and extraction-only metadata. Keep
   the rich generator inputs and existing server behavior.
2. Make compiler checking of those projected types the permanent constraint.
   The audit automatically reports new stored fields; require a reason to put
   each field in the startup pack rather than a detail/feature pack.
3. Re-run q11 measurements for all seven locales after each schema change.
   Add referential-integrity and affected-page checks alongside byte budgets.
4. Handle description/NPC deferral separately. Its approximately 0.98 MB
   opportunity is materially larger, but requires async consumers and correct
   initial SSR/hydration data. Lazy routes are outside this audit.

The [README](README.md) gives the repeatable commands and explains why lexical
reference counts, public-field dead-code warnings, and runtime traces cannot
individually establish liveness.
